# Milastoria — архитектура бэкенда (черновик решений)

Статус: обсуждается, ничего ещё не реализовано. Цель документа — зафиксировать
рассуждение, чтобы к нему можно было вернуться и оспорить, а не переизобретать
каждый раз заново.

## Контекст и ограничения

- Уходим с Tilda (магазинная механика) на галерею-лукбук собственной разработки.
  Визуальная часть уже есть: `prototype-v2/` (статический HTML/CSS/JS,
  данные пока захардкожены в `js/data.js`).
- Нужна небольшая админка: загрузка и кадрирование фото, водяной знак,
  SEO-поля (title/description/alt), публикация лота.
- ~50–200 карточек работ, у части — видео-фрагмент. Нагрузка околонулевая
  (посетители — потенциальные клиенты ателье, не десятки тысяч в день).
- Разворачивать самостоятельно: Docker-образ → VPS в РФ. Бюджет ориентируется
  на текущий платёж за Tilda (~750 ₽/мес) — после переезда эти деньги
  освобождаются, тратить на инфраструктуру предполагается не больше.
- Стек должен быть **реально понятным автору**, а не результатом
  ИИ-генерации, которую страшно чинить в одиночку. Это ограничение сильнее,
  чем «индустриальный стандарт» — см. ниже про выбор фреймворка.

## Выбор языка: Java

Знакомый язык — Java (второй вариант, если что-то не ляжет — Go).
Для проекта такого размера Java действительно объективно избыточна
по сравнению с, например, Go или даже Node — но это не аргумент против неё:
единственный язык, на котором вы реально распишетесь за каждую строчку,
это тот, который вы уже понимаете. Учить новый язык одновременно с
архитектурой веб-приложения — плохая идея, если цель «шарить», а не
"запустить любой ценой".

## Выбор фреймворка: Javalin

Spring Boot автору хорошо знаком («забит как гвоздь»), и это был
весомый довод в его пользу — но осознанно решено попробовать Javalin:
интересно на практике, плюс тонкая библиотека без скрытого DI-контекста
снижает риск незаметно натащить в маленький проект лишние слои и
конфигурацию «на вырост» (тот самый «ад», которого хочется избежать).

**[Javalin](https://javalin.io/)** — не фреймворк в смысле Spring, а
тонкая библиотека поверх Jetty: роутинг, middleware, статика — обычные
вызовы методов, без reflection-магии и бинов.

```java
Javalin app = Javalin.create(config -> config.staticFiles.add("/public"));
app.get("/work/{slug}", ctx -> {
    Lot lot = lotMapper.findBySlug(ctx.pathParam("slug"));
    ctx.render("work.jte", Map.of("lot", lot));
});
app.start(8080);
```

Вместе с ней — **MyBatis** для доступа к данным (уже выбран, знаком
автору): SQL пишется руками в `.xml`-мапперах или аннотациях, MyBatis
только маппит результат запроса на Java-объект — никакой скрытой
генерации запросов или ленивой загрузки, как у Hibernate. Структура:
интерфейс `LotMapper` с методами (`findBySlug`, `findByCategory`,
`insert`, ...) + сам SQL рядом. `SqlSessionFactory` конфигурируется
один раз при старте — MyBatis прекрасно живёт без Spring.

Общий принцип по слоям, который не зависит от выбора фреймворка:
`Controller → Mapper` напрямую там, где нет логики; `Service`
добавляется только когда логика реально появляется (генерация slug,
оркестрация загрузки фото), а не как обязательный слой по умолчанию.
Один модуль, один jar — пять сущностей не образуют границ, по которым
имело бы смысл резать проект на части.

## Хранение данных: SQLite

- Один файл `milastoria.db`, никакого отдельного контейнера БД.
- Драйвер `org.xerial:sqlite-jdbc`, схема — простой `schema.sql`,
  выполняемый при старте (миграции через Flyway можно добавить позже,
  когда/если схема станет часто меняться).
- Бэкап = скопировать файл. Восстановление = положить файл обратно.
  Никакого `pg_dump`/`mongodump`, никакой отдельной инфраструктуры
  для бэкапов.
- Данные по сути реляционные (лот → много фото → много тегов), это
  ложится на SQL естественно; документная БД (Mongo) здесь скорее
  усложнила бы модель, чем упростила.

### Схема (первое приближение)

```
categories (id, slug, title, cover_image, seo_text)
lots       (id, slug, title, category_id, annotation, seo_text,
            meta_title, meta_description, occasion, year,
            fabric_notes, client_name, featured, status, sort)
lot_images (id, lot_id, path_thumb, path_full, alt, caption, sort)
lot_videos (id, lot_id, path, poster_path, caption)
tags       (id, name)
lot_tags   (lot_id, tag_id)
```

Прямое отражение текущего `js/data.js` — переносить данные из прототипа
в таблицы будет механической задачей, не редизайном модели.

## Рендеринг: серверный (SSR), не JS поверх JSON

Важное отличие от `prototype-v2`: там HTML-сетки строит клиентский
`app.js` из `data.js` — для поисковика первая загрузка страницы почти
пустая. В реальном бэкенде HTML должен собираться на сервере —
шаблонизатор [jte](https://jte.gg/): компилируется в Java-байткод,
опечатка или переименованное поле модели ломает сборку, а не тихо
показывает пустое место в проде. Общий layout (шапка/нав/футер,
одинаковые на всех страницах) — отдельный `.jte` с параметром
`gg.jte.Content`, остальные шаблоны передают в него своё содержимое.

**Реализовано** (`backend/src/main/jte/`, `SiteController`):
`/`, `/gallery` (фильтры `?category=`/`?tag=`/`?q=` — query-параметры,
не сегменты пути: проще на MyBatis dynamic SQL, а URL всё равно
получается стабильным и индексируемым для каждой комбинации),
`/work/{slug}` (path-параметр). CSS и клиентский `site.js` (лайтбокс,
мобильное меню, переключение миниатюр — через `data-*` атрибуты,
без JS-модели данных) перенесены из `prototype-v2` почти без
изменений — это progressive enhancement поверх готового HTML.

Не сделано пока: JSON-LD (`Product`) на странице лота — упоминалось в
черновике прототипа, но в перенос не попало; добавить, когда дойдём
до финальной вычитки SEO-полей.

## Обработка изображений

Реализовано и покрыто тестом: `backend/src/main/java/ru/milastoria/image/`
(`ImageProcessor`, `CropRect`) + `ImageProcessorTest`.

### Формат кропа (закрытый открытый вопрос №1)

Клиент (Cropper.js) отдаёт прямоугольник кропа в пикселях **оригинала**
(`cropper.getData()`) — не проценты, не canvas-blob. Оригинал хранится
на диске без изменений всегда; ImageMagick режет из него заново при
каждом рендере вариантов. Решение в пользу этого варианта, а не
"кроп сразу в canvas и отправить готовую картинку":

- переснятый кроп не теряет качество на повторном пережатии — правка
  кадрирования не означает деградацию каждый раз;
- всё пиксельное преобразование в одном месте (ImageMagick), браузер
  только помогает человеку выбрать рамку, а не обрабатывает пиксели;
- меньше форматов на входе бэкенда: всегда «оригинал + 4 числа», а не
  иногда ещё и сжатый браузером JPEG с непредсказуемым качеством.

### Кодирование ImageMagick (запрос: "культурный" размер на выходе)

`ImageProcessor` строит команду `convert` как массив аргументов
ProcessBuilder (не строку через шелл — поэтому скобки `(`/`)` и `>` не
экранируются, это просто отдельные элементы argv):

```
convert ORIGINAL -auto-orient \
  -crop WxH+X+Y +repage \
  -resize {maxEdge}x{maxEdge}\> \
  -strip -interlace Plane -quality {q} \
  ( watermark.png -resize {wmWidth}x ) -gravity SouthEast -geometry +{m}+{m} -composite \
  OUTPUT.jpg
```

Два варианта на каждый кадр:

| Вариант | Макс. сторона | JPEG quality | Для чего |
|---|---|---|---|
| `full`  | 1800px | 84 | лайтбокс, страница лота |
| `thumb` | 900px  | 82 | карточки в сетке |

Проверено на настоящем исходнике из `Сырье/` (3657×5998, ~5.05 МБ,
формат прямо с камеры): `full` — 316 КБ, `thumb` — 98 КБ. Порядок
операций важен: `-auto-orient` до `-crop`/`-strip` — ориентация из
EXIF применяется к пикселям первой, и только потом метаданные (вместе
с GPS-координатами места съёмки — а это часто фото детей) можно
безопасно выбросить. `-resize ...\>` не увеличивает картинку, если она
уже меньше лимита. `-interlace Plane` — прогрессивный JPEG.

Водяной знак — существующий `watermark.png` из корня репозитория
(настоящий, с альфа-каналом, уже используется в проде), скопирован в
`backend/src/main/resources/branding/`. Так как `convert` — внешний
процесс, ему нужен реальный путь в файловой системе, а не classpath-
ресурс: `ImageProcessor.extractBundledWatermark()` один раз копирует
его на диск рядом с данными при старте приложения.

Возможное развитие (не в v1): параллельно с JPEG отдавать WebP через
`<picture>` — тот же `convert` с `-quality 80` и расширением `.webp`,
дополнительная пара строк, когда дойдут руки.

Готовые файлы лежат на диске в volume контейнера, не в БД (в БД —
только пути `path_thumb`/`path_full`). Объектное хранилище
(S3-совместимое, например Selectel/Yandex) — опция на будущее, если
фото станет действительно много; на старте не нужна.

## Админка и авторизация

**Реализовано** (`backend/src/main/java/ru/milastoria/web/Auth.java`,
`AdminController`, `admin/*.jte`):

- Один пользователь-админ. Пароль — обычный текст в переменной
  окружения `ADMIN_PASSWORD`, хешируется (SHA-256) в приложении при
  старте; сравнение через `MessageDigest.isEqual` (constant-time).
- Сессия — подписанная HMAC-SHA256 кука без состояния на сервере
  (никакой таблицы сессий): payload — время истечения, подпись —
  HMAC по ключу `SESSION_SECRET`. `before`-хендлер Javalin на `/admin`
  и `/admin/*` — **оба паттерна нужны отдельно**: `/admin/*` не матчит
  голый `/admin` без хвоста, это реальный баг, который поймал на
  этапе проверки (без второй регистрации дашборд был доступен без
  логина).
- Формы — обычный HTML + Cropper.js 1.6.2 для кропа (CDN), без SPA.
  Библиотека зафиксирована на мажорной версии 1.x: актуальная 2.x —
  совсем другой API (веб-компоненты), мигрировать на неё заодно с
  загрузкой не стали.
- Загрузка — один запрос: `<input type=file>` без атрибута `capture`
  (чтобы iOS показал оба варианта — «Библиотека фото» и «Сделать
  фото», не только камеру), Cropper.js крутит превью локально через
  `URL.createObjectURL` без обращения к серверу, по кнопке «Готово»
  обычный `<form>` с файлом и координатами кропа (`x`,`y`,`width`,
  `height` из `cropper.getData()`) уходит одним POST. Никакого
  двухфазного upload/temp-file протокола не потребовалось.
- Оригинал сохраняется в `CONTENT_DIR/originals/`, thumb/full — в
  `CONTENT_DIR/img/`, названы `{slug}__{sort}.jpg` /
  `{slug}__{sort}__full.jpg` — тем же паттерном, что и в seed-данных.

### Требование: загрузка фото простая до безобразия и удобна на iPad

Явный запрос — админка будет использоваться в первую очередь с iPad
(реально, во время/после съёмки), не с десктопа с мышью. Это меняет
конкретные решения по UI загрузки, не только "сделаем адаптивно":

- **Выбор файла — нативный `<input type="file" accept="image/*">`**, не
  кастомная drag-and-drop-зона. На iPad Safari перетаскивание файла
  жестом из приложения «Фото» в браузер ненадёжно; нативный пикер сразу
  даёт системный выбор «Библиотека фото / Сделать фото» без единой
  строчки своего кода.
- **Один экран — один шаг.** Не общая форма со всеми полями сразу, а
  последовательность: (1) выбор фото → (2) кроп на весь экран, один
  жест, одна кнопка «Готово» → (3) заголовок/категория/теги отдельным
  простым шагом, не обязательно сразу же. Меньше решений на экране —
  меньше промахов пальцем.
- **Контейнер Cropper.js — на всю доступную высоту вьюпорта**, не
  фиксированные пиксели: должен нормально занимать экран и в
  портретной, и в альбомной ориентации iPad. Pinch/drag для кропа
  Cropper.js поддерживает из коробки, доп. код не нужен.
- **Категории — крупные кнопки-переключатели, не `<select>`** — на
  4–5 категорий тап по крупной кнопке быстрее, чем открывать колесо
  выбора пальцем.
- **Тач-мишени ≥44×44pt** (минимум Apple HIG) — любая кнопка/крестик
  закрытия/ссылка с запасом под палец, а не только под курсор мыши.

## Docker и деплой

```
┌───────────────────────────────────────┐
│         VPS (Docker, РФ-провайдер)      │
│                                         │
│   ┌────────┐      ┌──────────────────┐ │
│   │ Caddy  │─────▶│  milastoria-app   │ │
│   │ :80/443│      │  (java -jar ...)  │ │
│   └────────┘      └─────────┬─────────┘ │
│                              │           │
│                     volume: /data        │
│                     ├── milastoria.db    │
│                     └── uploads/*.jpg    │
└───────────────────────────────────────┘
```

- **Dockerfile**: multi-stage — сборка (Maven/Gradle) в одном слое,
  рантайм — `eclipse-temurin:21-jre-alpine` + `apk add imagemagick`.
  Без JDK и билд-инструментов в финальном образе.
- **docker-compose.yml**: сервис `app` + сервис `caddy`
  (реверс-прокси, автоматический TLS через Let's Encrypt — работает
  из РФ без проблем, это просто DNS + ACME, не завязано на
  зарубежную CDN-инфраструктуру).
- **Бэкап**: cron внутри VPS, копирующий `/data` куда-то ещё
  (например, rclone в Яндекс Object Storage раз в сутки).
- **Хостинг**: Timeweb Cloud / Selectel / VK Cloud / Beget — Docker
  из коробки, оплата российской картой. Бюджет ~750 ₽/мес закрывает
  тариф в районе 2 vCPU / 2–4 ГБ RAM / 30 ГБ NVMe — Javalin стартует
  быстро и не тянет за собой тяжёлый DI-контекст, так что даже 1–2 ГБ
  RAM были бы комфортны; запас в этом тарифе на будущее. Точные тарифы
  уточнять на момент покупки, они меняются.

## Явно вне рамок v1 (чтобы не тонуть в скоупе)

- Многопользовательская админка / роли.
- Объектное хранилище вместо локального диска.
- Полнотекстовый поиск отдельным движком (хватит `LIKE`/FTS5 SQLite).
- Очереди/асинхронная обработка видео — видео просто отдаём как есть.
- CI/CD пайплайн — на старте достаточно `docker compose build && up -d`
  руками или по SSH; автоматизацию через GitHub Actions добавить
  можно позже, когда появится, что автоматизировать.

## Черновики лота (закрытый открытый вопрос №2)

Оставляем — но в самом дешёвом виде. `status` уже есть в схеме
(`schema.sql`: `status TEXT NOT NULL DEFAULT 'draft'`), никакой
отдельной таблицы версий, истории изменений или превью-ссылок не
заводим. Вся "фича" — это:

- публичные запросы (`LotMapper.findFeatured`, будущий `findPublished`)
  всегда фильтруют `WHERE status = 'published'`;
- в админке — один переключатель черновик/опубликован на форме лота.

Это не overengineering ровно потому, что стоимость уже равна нулю —
поле и так нужно было для сортировки. Не заводить его значило бы
редактировать SEO-текст и фото лота прямо на живой публичной странице,
а не как черновик — то есть сознательно хуже.
